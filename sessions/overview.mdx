A session is one conversation with your Script.it agent. In a session you ask the agent to build a script, run it, explain a result, or fix a failure, and you watch it work. The agent keeps the context of the whole conversation, so you can iterate without repeating yourself.

## What a session holds

Each session keeps its own:

- **Conversation** — your messages, the agent's replies, and the steps it took.
- **Files** — the session's **Session Files**: attachments you send and everything its runs write. See [Session files](/sessions/files).
- **Model** — the AI model the agent uses, picked in the composer. See [Models](/sessions/models).
- **Permission profile** — what the agent may do in this session, picked in the composer. See [Permission profiles](/governance/permission-profiles).
- **Scripts it touched** — shown as chips above the message box, each marked **new**, **updated** or **removed**.

## Sessions and scripts

A **script** is a reusable workflow saved in a workspace. A **session** is where you build and run it.

- When the agent changes a script, the change is saved to the script's workspace. Everyone who can see that workspace sees the new version.
- Script.it saves a version of the script at the end of every agent turn that changed it. You can restore any earlier version from the script's history. See [Outlines, comments, and history](/scripts/outline-and-history#history).
- Files a run produces belong to the session that ran it, not to the script. Running the same script in two sessions never mixes their outputs.

## Where sessions come from

| How it starts | Where it appears in the **Sessions** list |
|---|---|
| You click **New session** at the bottom of the sidebar, or press `Cmd+Shift+S` (`Ctrl+Shift+S` on Windows) | **Opened** |
| You click **Run** on a script's page and confirm the run | **Opened** |
| A trigger runs a script | **Triggered** |
| You message your agent by email, Slack, Teams, Telegram or WhatsApp | One session per conversation. See [Ways to reach your agent](/channels/overview). |

A new session stays a draft until you send its first message, so opening one and leaving creates nothing.

Work that a session starts can get its own **sub-session**, listed under the session that started it: an Agent a script runs, a subagent the agent hands work to, or a script run that continues after a wait. See [Managing sessions](/sessions/managing#sub-sessions).

## Your sessions are yours

Sessions belong to you and to the account you're working in. Switching between your **Personal** account and an organization shows that account's sessions. Teammates in a shared workspace see the scripts you change, not your sessions. The exception is a session you choose to include when you publish a script. See [Publishing](/scripts/publishing).

## Picking up where you left off

Session history persists. Leave a session and come back later: the conversation, files and model are where you left them, and the agent still has the context.

If your environment is asleep when you come back, a session you opened recently shows its latest messages right away, read-only, while the environment starts. You can send again once the session finishes loading.
